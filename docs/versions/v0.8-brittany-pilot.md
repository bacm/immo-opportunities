# v0.8 — Pilote Bretagne

**État :** En cours — socle technique livré, gate régional bloqué par les données et le terrain  
**Dépend de :** v0.7

## Objectif utilisateur

Valider que le produit détecte et aide à qualifier des candidats utiles sur les principaux segments des quatre départements bretons.

## Inclus

- partitionnement des pipelines sur les départements 22, 29, 35 et 56 ;
- rapports d’acceptation DS-01 à DS-09 pour chaque territoire ;
- couverture par département, EPCI et commune ;
- audits urbain, périurbain, littoral et rural ;
- recalibrage versionné des segmentations et seuils ;
- dataset interne `CandidateReview` ;
- protocole aveugle top score, baseline et échantillon aléatoire ;
- administration des releases et publication régionale ;
- staging et production ;
- sauvegardes PostgreSQL, réplication MinIO et restauration testée ;
- pilote avec au moins trois professionnels ;
- décision documentée `poursuivre / pivoter / arrêter`.

## Hors périmètre

- extension au-delà de la Bretagne ;
- vacance, orthophotos temporelles ou vision ;
- apprentissage supervisé ;
- fonctionnalités commerciales non nécessaires au protocole du pilote.

## Validation régionale

Les métriques sont calculées globalement et séparément pour :

- chaque département ;
- pôles urbains et métropolitains ;
- villes moyennes ;
- couronnes périurbaines ;
- marchés littoraux et touristiques ;
- territoires ruraux.

Une moyenne régionale favorable ne compense pas une dégradation critique non documentée dans un segment.

## Dataset de validation

`CandidateReview` conserve snapshot, stratégie, évaluateur pseudonymisé, décision, motifs, confiance de la revue et résultats métier successifs. Un sous-échantillon est évalué deux fois et les désaccords sont conservés.

Le jeu final de validation est séparé temporellement et géographiquement des données utilisées pour ajuster les règles.

## Exploitation

- déploiement GitHub Actions/Ansible reproductible ;
- restauration sur un serveur vierge ;
- mesure RPO/RTO ;
- alertes sur fraîcheur des sources, imports et sauvegardes ;
- runbooks d’incident et de retrait d’une release ;
- tableau de bord coût, capacité et performance.

## Tests obligatoires

- imports complets et reprise par partition ;
- non-régression de couverture entre releases ;
- précision top 10/20/50 contre baseline ;
- analyse par segment et stabilité du classement ;
- test de charge carte, liste, API et tuiles ;
- restauration PostgreSQL et MinIO ;
- isolation organisationnelle en production ;
- retrait d’une source défectueuse ;
- exercice de publication et rollback d’un snapshot.

## Critères d’acceptation

- la Definition of Done MVP de `SPEC.md` est entièrement tracée ;
- aucun département n’est présenté comme couvert sans données critiques suffisantes ;
- H1 à H5 disposent d’un résultat mesuré ;
- le top 20 dépasse la baseline selon le seuil convenu ou le résultat négatif est documenté ;
- au moins trois professionnels utilisent le produit sur des cas réels ;
- au moins deux acceptent un pilote payant ou engagement équivalent ;
- une décision de poursuite est formellement prise.

## Démonstration attendue

Depuis une infrastructure vierge, restaurer ou redéployer la plateforme, publier une release Bretagne, réaliser un parcours professionnel complet et présenter les résultats de validation par segment.

## Risques

- élargir la couverture avant de corriger les écarts de qualité ;
- ajuster le score sur le jeu final ;
- confondre activité utilisateur et valeur métier ;
- poursuivre malgré un lift insuffisant contre baseline.

## Definition of Done

- [ ] DS-01 à DS-09 audités sur les quatre départements.
- [ ] Couverture et limites publiées par territoire.
- [ ] Scores validés contre baseline par segment.
- [ ] Pilotes professionnels réalisés.
- [ ] Sauvegarde, restauration et exploitation éprouvées.
- [ ] DoD produit et architecture entièrement tracées.
- [ ] Décision `poursuivre / pivoter / arrêter` publiée.
